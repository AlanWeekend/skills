# 对象身份、版本与数据流转

本参考不指定主键类型或 ID 算法。先沿用项目已有契约，再补齐生命周期和导入规则。

## 最小逻辑模型

以下只表示身份关系，字段名和约束按实际项目确定：

```text
content_document.id                 文档对象的稳定身份，也可以直接作为主键
content_document_version.id         单条版本记录的身份
content_document_version.document_id 该版本所属文档的稳定身份
content_document_version.version    同一文档范围内的版本号
```

- 同一文档发布多个版本时，`content_document.id` 不变；版本记录分别拥有自己的记录身份。
- 若业务要求一个文档不能重复发布同一版本号，可约束 `(document_id, version)` 唯一；不能只因存在这两个字段就假设已有约束。
- 如果所有版本记录也需要跨系统引用，应单独说明它们的标识和唯一范围。
- 简单实体、关联或快照有自己的适用结构，不为套用此示例强行拆版本表。

## 明确每种操作的身份变化

| 操作 | 默认身份语义 | 需要另外决定的内容 |
| --- | --- | --- |
| 改名、修改配置 | 仍是原对象 | 乐观锁、审计或版本规则 |
| 发布新版本 | 对象身份不变，新建版本记录 | 版本号唯一范围、当前版本引用 |
| 复制为新对象 | 分配新对象身份 | 子对象复制、共享引用和来源记录 |
| 将同一对象搬到另一环境 | 保留身份，或维护显式映射 | 唯一性假设、引用和租户映射 |
| 将导出包导入为新副本 | 创建新身份，并重写对应引用 | 外部依赖、重试和重复导入策略 |
| 恢复备份 | 保持备份中的身份关系 | 恢复到空库还是合并到已有环境 |

“迁移”“导入”“复制”不是同义词。先确定产品操作的真实语义，不能仅根据按钮名称决定是否保留 ID。

## 导入和合并流程

1. 确认来源系统或部署、对象种类、来源标识、目的范围，以及这是迁移同一对象还是创建副本。
2. 核对是否需要转换本地记录键；导入映射至少要能区分来源命名空间、对象种类和来源标识，必要时包含租户。
3. 先识别重复与冲突，再按既有产品策略更新、跳过、拒绝或创建副本；不能通过显示名称静默合并。
4. 根据依赖顺序创建对象或预分配标识，再重写关系、版本归属及嵌入配置中的引用；循环依赖按项目机制处理。
5. 使用独立的导入任务或幂等规则处理重试；同一导入包是否可多次创建副本属于产品决策，不能仅凭对象 ID 猜测。
6. 对账对象数量、映射完整性、引用可解析性和失败恢复结果。发现无法映射的引用时，按明确策略报告或拒绝。

两个系统都存在 `id = 42`，既不能说明它们是同一个对象，也不能说明它们一定不同；判断依赖来源和身份契约。相同算法或相同名称同样不能代替这个契约。

## 兼容性与评审清单

- 将外部接口、消息、缓存键、审计及文件引用纳入 ID 兼容性检查，不把数据库主键重命名当成局部无影响的改动。
- 已有数字主键不必一律替换；如果跨环境流转有冲突，可评估稳定对象标识或导入映射，选取满足实际需求的最小方案。
- 即使使用 UUID，也要明确由谁分配、能否由客户端指定、如何处理碰撞与重复提交；标识本身不承担访问授权。
- 人类可读的业务编码只有实际需求才引入；其可修改、别名和回收规则与机器对象身份分别确定。
- 删除后重新创建、归档后恢复和租户间转移的身份语义需要明确；不擅自将已删除 ID 分配给另一个对象。
- 涉及生成器或类型变更时，提供存量兼容、引用迁移及回滚方案；不把本任务扩展成没有业务依据的全库换键。

至少推演：改名、发版、复制、重复导入、跨来源相同局部 ID、缺失依赖及客户端标识往返。无法运行时明确这是设计审查，不能宣称已验证迁移成功。
