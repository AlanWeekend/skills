# 中文注释审查

帮助中文读者判断源码是否具备足够、可信的阅读说明。默认只审查；用户同时要求修正时，才在授权范围内修正。此 Skill 自包含，不要求安装写作类 Skill。

## 审查顺序

1. 确认本次范围、项目已有规范及生成 / 第三方文件排除项；按实际 diff 与必要上下文阅读源码。
2. 先核对现有注释与实现是否一致，再检查缺失说明。错误的权限、事务、返回值或异常说明比措辞问题更优先。
3. 从文件用途、接口契约、内部流程三个层次检查；复杂语法是否得到与当前代码相关的中文解释。
4. 用实际文件和行号报告问题，解释缺失或错误如何妨碍理解，并给出具体补充方向；不以注释数量或行数比例打分。

## 分语言检查

| 范围 | 重点 |
| --- | --- |
| 所有源码 | 文件用途是否具体，关键函数与业务分支是否能理解，中文与标识符是否对应，是否有过期注释或虚构保障 |
| JS / TS | 函数参数、结果、副作用与异常，类型与字段的语义，可选值、联合类型和重要回调的作用 |
| Vue | 页面 / 组件用途，Props / Emits / Slots 契约，状态来源、响应式与卸载流程，模板业务区块和条件链安全 |
| Python | 模块、类和函数的 Docstring 位置与识别，Args / Returns / Yields / Raises 的真实性，以及内部步骤说明 |

## 反馈边界

- 区分“与实现矛盾”“关键说明缺失”“表达可改善”，只按真实影响说明优先级，不把普通措辞偏好升级为运行缺陷。
- 每条问题说明实际行为、当前注释或缺口、对读者的影响和建议；只有有证据的运行问题才作为运行风险报告。
- 对文档无法确认的业务约定，说明待确认信息，不要求凭空添加结论。
- 不因审查强行重构、增加类型、安装 lint 工具或扩大到整个仓库。
- 没有发现问题时直接说明，并说明检查范围及不能验证的部分；不凑问题或宣称审查证明了程序正确性。
