# 中文规范 Git 提交

为不同项目提供一致、可验证的中文提交流程。只在任务包含编写提交信息、创建提交或推送时使用，不把安装 Skill 视为提交或推送授权。

## 提交信息

- 格式为 `<type>(<scope>): <中文描述>`；scope 可省略。确有破坏性变更时，按仓库约定使用 `!` 或 `BREAKING CHANGE:` 页脚，并用中文解释影响及迁移要求。
- 默认 type 使用 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert`。scope 与已有项目命名保持一致。
- 标题描述及正文使用简体中文；类型、范围、必要标识符、命令、技术名称及工具要求的页脚标签保留英文。不为凑格式添加正文或编造变更。
- 仓库存在 commitlint 配置时优先遵循配置；尚无配置时按 `@commitlint/config-conventional` 校验，不为一次提交擅自创建根 npm 项目或改写已有 lint 配置。
- 描述准确表达实际变更，正文需要时解释原因、主要影响及验证限制。不要把未完成或未验证的行为写成已实现。

## 确认范围与校验

1. 阅读相关代理规则、当前分支、Git 状态、提交配置和任务上下文；确认用户授权的是提交、推送还是仅生成提交信息。
2. 检查工作区及原暂存区。明确区分当前任务与无关改动；不要撤销、清空或直接提交他人已经暂存的工作。
3. 根据实际变更运行针对性验证。目录或文档变更检查结构、链接与适用格式，不宣称运行了不存在的应用测试。
4. 只暂存确认的任务文件或相关补丁，检查完整暂存差异、异常文件和空白问题；不盲目使用 `git add .`。
5. 使用仓库已有 commitlint 命令或可正确解析官方 preset 的临时 CLI 环境校验拟提交信息；保留现有 hooks、签名和仓库检查，不擅自跳过失败检查。
6. 紧邻提交前重新核对 HEAD、暂存文件范围及暂存树或等效摘要。发现并发变化先重新审查，不按旧快照提交。

## 提交与推送

- 提交信息通过可靠的参数或 UTF-8 文件传入 Git，避免 shell 转义和 Windows 编码破坏中文；文件方式见 [references/examples.md](references/examples.md)。
- 创建提交后读取真实提交 ID、标题、提交范围及剩余状态；不以命令已发出代替成功结果。
- 用户只要求提交时不 push；已明确授权推送时直接在授权范围内执行，不重复索要相同授权。
- 推送前核对目标 remote 和分支，检查远程变化，使用普通快进推送；不自行 force push、改写已发布历史或更换远程地址。
- 遇到远程更新，先检查并保留本地任务和用户改动，再按仓库允许的方式整合；不能安全完成时说明具体冲突或阻塞，不覆盖远程。
- 推送后核对远程目标分支包含预期提交，再报告成功。最终说明提交 ID、中文标题、验证结果、是否推送及未提交改动。

详细类型示例、临时校验注意事项和中文编码示例见 [references/examples.md](references/examples.md)。此 Skill 的必要资料均在自身目录，不依赖个人路径或其他 Skill。
